# 加了 'R' 记录，format_ver 要不要升到 3

Type: grilling
Opened: 2026-09-19
Status: resolved
Blocked by: -

## Question

`record_is_structurally_valid()`（`owner_slot.c:75`）现在要求三件事全中才算有效：

```
type == 'O'  &&  slots == 5  &&  format_ver == 2
```

所以**旧 bootloader 见到一条 `'R'` 记录会判它无效并跳过** —— 也就是在一块已经下发过撤销的板子上，旧固件会**忽略撤销，照常放行被撤的那个人**。这是 fail-open。

反方向也要想：新 bootloader 见到只有 `'O'` 记录的旧板子，应该照常工作（没有撤销状态 = 谁都不撤）。

要定的是：

| 选项 | 后果 |
|---|---|
| **升到 3** | 旧记录全废，硬切。已认领的板子升级 bootloader 之后**所有权直接丢失** —— 而原地升级的全部意义就是保住它 |
| **保持 2，`'R'` 靠 `type` 区分** | 新旧共存，但旧固件静默忽略撤销 |
| **别的**（比如给 `flags` 加一个「本区含撤销记录，不认识就拒绝启动」的位） | fail-closed，但会让旧固件把板子停住 |

⚠️ 这张票**被 [撤销记录点名的是序号还是公钥](OWN-01-revoke-by-serial-or-by-pubkey.md) 挡着** —— `'R'` 记录长什么样还没定，格式版本的问题问不清楚。

## 怎么算答完

定下 `format_ver` 的取值和理由，并把**两个方向**的行为各写一句：

- 旧 bootloader 遇到新记录，会怎样
- 新 bootloader 遇到旧板子（只有 `'O'` 记录），会怎样

判据要能判真假 —— 比如「旧固件启动日志里出现 `N record(s) ignored - wrong format`，且 `getpubkey` 仍返回原主人」这种。

## Answer

2026-09-19 定。**`OWNER_FORMAT_VER` 升到 3，硬切，不做兼容路径。**

被迫升，不是选择：用户当天决定「被新逻辑取代的字段一律删」，落到 `owner_record_t.slots` 和证书的 `serial`
两处，**记录布局和证书长度都变了**（证书 132 → 128 字节），v2 的字节拿来没有任何安全的用法。

`record_is_structurally_valid()` 见到 `format_ver != 3` 直接判无效，和当年 v1 → v2 同一个做法。
**现场没有已认领的板子**，所以这是一次硬切而不是迁移。

两个方向的行为：

| | 行为 |
|---|---|
| 旧 bootloader 遇到新记录 | 判无效并跳过 → 板子回落内置公开根。**不是静默** —— 启动日志打 `N record(s) ignored - wrong format or corrupt` |
| 新 bootloader 遇到旧板子（只有 v2 记录） | 同样判无效 → 回落内置根 → 要重新 `takeown` |

⚠️ **这条抵消了原地升级的一部分价值**：装着 v2 记录的板子升到新 bootloader 之后，
所有权仍然会丢。**原地升级保住所有权这条性质，从 v3 之后的版本之间才成立。**

⚠️ **开这张票时写的「被 `'R'` 记录长什么样挡着」不成立** —— 删字段这个决定和 `'R'` 的形状无关，
它自己就把格式版本推到了 3。所以 `Blocked by` 已改回 `-`。

## 引出了什么新的未知

**有一条**：手上那块板如果已经认领过（v2 记录），升级到 v3 固件时会丢所有权，
**需要一次手工重新认领**。这不是设计问题，是切换那一次的操作步骤 ——
已记进 [要改的东西，一条不落](../CHANGE-LIST.md)。
