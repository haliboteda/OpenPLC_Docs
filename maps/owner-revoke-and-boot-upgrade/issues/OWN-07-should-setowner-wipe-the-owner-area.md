# 换根的时候把 owner 区清空重写

Type: grilling
Opened: 2026-09-20
Status: resolved
Blocked by: -

## Question

用户 2026-09-20 提出：**换根（`setowner`）时把 `'O'` 和 `'R'` 两段全部清空、重新写**。

这能真正回收作废名额 —— 换根之后旧根签发的叶全部失效，那些 `'R'` 记录记的东西已经没有约束力，
清掉它们不丢任何有效信息。没有这一步，`'R'` 段满了就只剩「重烧 bootloader」一条路
（见 [要改的东西，一条不落](../CHANGE-LIST.md) 的 `I-D2`）。

### 硬约束：清空 owner 区 = 擦掉 bootloader 自己

owner 区在 `0x0801E000`–`0x0801FFFF`，bootloader 在 `0x08000000`–`0x0801DFFF`，
**同属扇区 0**（128 KiB），而 flash 能擦的最小单位就是一个扇区。

所以「清空 owner 区」必然是：读 bootloader 自己进 SDRAM → 擦扇区 0 → 写回 bootloader + 新记录。
擦写例程必须在 `RAM_D1` 里跑、全程关中断 ——
见 [擦扇区 0 的时候，那段代码从哪执行](OWN-02-where-does-the-erase-code-run.md)。

**这会改变 `setowner` 的风险等级：**

| | 今天 | 清空重写之后 |
|---|---|---|
| 做什么 | 追加一条 160 字节记录 | 擦掉并重写整个扇区 0 |
| 掉电 | 最多留一条废记录，板子照常启动 | 板子起不来，**按 BOOT0 进 DFU → USB 重刷 bootloader 和 app → 重新授权** |
| 需要的机制 | 无 | `RAM_D1` 擦写例程 + SDRAM 暂存 —— 和 `flashboot` 原地升级是**同一套** |

### 用户 2026-09-20 澄清的形状（④）

**不是每次换根都清空，只在快满的那一次清。**

| 时机 | 命令 | 板子做什么 | 掉电风险 |
|---|---|---|---|
| 平时换根 | `IAPTool setowner ...` | 在 `'O'` 段追加一条记录（今天的行为） | 最多留一条废记录 |
| `'O'` 或 `'R'` 剩 8 条 | —— | 启动日志提示：考虑换根重授权并清空 | —— |
| 用户决定清空 | `IAPTool setowner --wipe ...` | 读 bootloader 进 SDRAM → 擦扇区 0 → 写回 bootloader + 新 `'O'` 记录，两段全空 | 掉电要**走一遍 DFU 重刷 + 重新授权** ¹ |

⚠️ **清空必须是显式请求的，不能由板子自己判断。**
板子一旦检测到快满就把这次 `setowner` 悔成擦写流程，
用户就在**不知情的情况下**承担了一次掉电重刷的风险 —— 他以为自己在做日常操作。
提示归提示，动作要他自己选。

**generation 怎么算**：清空后新 `'O'` 记录的 generation **延续清空前的最大值 + 1**，不从 1 重开。
（重置在安全上也站得住 —— 重放的旧记录签名对不上新根，链会断 ——
但延续让「这块板换过几次主人」这个事实不因为一次清空就丢。）

### 三个早先的方向（④ 出现之前提的，保留作对照）

| | 做法 | 代价 | 取舍 |
|---|---|---|---|
| ① | **绑定 `flashboot`**：只在 bootloader 原地升级时压缩，`setowner` 保持今天的低风险追加 | 0（`A12` 本来就规划了「写回时压缩」） | 名额回收要等到下次升级 bootloader 才发生，**不能按需回收** |
| ② | **`setowner` 也走那套擦写**：每次换根都清空重写 | 换根变成高风险操作 | 名额随时能回收，但**每次换根都押上一次 DFU 重刷的风险** |
| ③ | **单独一条压缩命令**：不绑在换根上，要回收时显式调用 | 多一条命令 + 一条用例 | 风险只在显式调用时承担，换根保持低风险 |

## 怎么算答完

1. 选定一个方向，写进 [M2 归属与信任](../../../docs/modules/M2-ownership.md)
2. **说清掉电窗口有多长**，以及掉电之后怎么救（和 `flashboot` 用同一段文案，两处不重复）
3. 如果选 ② 或 ③，`ACCEPTANCE-CHECKLIST.md` 的 `CHK-B` 要加一条「清空重写走一遍」

⚠️ **这张票的三个方向都依赖 `RAM_D1` 擦写例程**，而那套东西属于 `flashboot` 原地升级那半边，
今天一行没写。所以这张票**可以现在定方向，但实施必然排在 `flashboot` 之后**。


## Answer

2026-09-20 定。**选④：按需清空，且必须显式请求。**

平时换根仍然只在 `'O'` 段追加一条记录（今天的行为、低风险）；
`'O'` 或 `'R'` 剩 8 条时启动日志提示用户考虑换根重授权；
用户决定清空时才用 `IAPTool setowner --wipe`，那一次才走擦扇区 0 的流程。
**板子不得自己判断要不要清空** —— 提示归提示，动作由用户选。

清空后新 `'O'` 记录的 generation **延续清空前的最大值 + 1**，不从 1 重开。

¹ **掉电的代价比看上去小**：恢复动作是「DFU 重刷 bootloader 和 app + 重新授权」，
而用户按下 `--wipe` 时本来就在做「换根重授权」—— **两者基本重合**。
所以这个操作掉电丢的不是板子，是一次重刷的时间。
（「掉电不是砖」已经是这张图定下的结论，2026-09-18 实测过 11 次。）

已记在 [要改的东西，一条不落](../CHANGE-LIST.md) 的 `A12`。
