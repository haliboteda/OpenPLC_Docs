# 校准值和 metadata 怎么共用扇区 15

Type: grilling
Opened: 2026-09-21
Status: resolved
Blocked by: -

## Question

去掉 journal 的事件日志之后，扇区 15（`IAP_STATE_SECTOR_ADDR`，`0x081E0000`，128 KiB）要同时装两样东西：

| | 要什么 | 冲突在哪 |
|---|---|---|
| **校准值** | **必须能覆盖** —— 重新标定要改得掉 | NOR flash 上「能覆盖」最终要擦整扇区 |
| **firmware metadata** | 每次升级追加一条，启动时验签要用 | 擦扇区会把校准值一起带走 |

⚠️ 这正是 [`DECISIONS.md` 第 45 条](../../../docs/tables/DECISIONS.md) 那个既存冲突：
原设计让 `journal_reclaim()` 搬运校准值，而**搬运期间掉电会丢校准值，重刷固件救不回来**。

## 怎么算答完

1. 给出扇区 15 的**逐段布局**：谁在哪、多大、固定地址还是 append
2. 写明**三条写入路径**各自擦什么、什么时候擦、掉电了会丢什么
3. 指出**唯一那个无人值守的掉电窗口**，并给出它的兜底办法
4. 算出 metadata 的容量（多少次升级满一次）

## Answer

2026-09-21 定（用户提的方案 + 两处改进）

### 1 · 布局

```
0x081E0000  ┌─ 校准值区 8 KiB ─────────────────────┐
            │  固定地址，不 append                  │
            │  工装经 JLINK 写；固件不提供写入命令   │
0x081E2000  ├─ metadata 区 120 KiB ────────────────┤
            │  append，一条 7 个 flash word = 224 B │
            │  最后一条生效                         │
0x081FFFFF  └───────────────────────────────────────┘
```

**容量**：120 KiB ÷ 224 B = **548 条**，即 548 次升级满一次。

### 2 · 三条写入路径

| 路径 | 谁在场 | 频率 | 擦什么 | 掉电后果 |
|---|---|---|---|---|
| **工装写校准值** | **人在场** | 出厂 + 偶尔重校 | 读校准值区到 RAM → 擦整扇区 → 写回 | ✅ 当场重来 |
| **升级写 metadata** | 无人值守 | 548 次里的 547 次 | **不擦任何东西**，纯 append | ✅ 校准值零风险 |
| **metadata 区满** | 无人值守 | 548 次升级一次 | 读校准值 8 KiB → 擦整扇区 → 写回校准值 + 一条新 metadata | ⚠️ **唯一的风险窗口** |

### 3 · 两处改进（相对用户原方案）

**① metadata 满了不用「读出来拼好再重写」—— 旧的本来就该丢。**
今天 `journal_reclaim()` 的注释已经写着 *"The old metadata is deliberately not carried over"*：
**548 条里只有最后一条有用**。所以要搬的只有校准值那 8 KiB，不是整个 128 KiB，
掉电窗口小一个数量级。

**② 工装写校准值时按板子 UID 留一份副本。**
这把唯一那个窗口的后果从**不可恢复**（要回产线重新标定）降成**可恢复**（重写一次）。
成本几乎为零 —— 工装本来就有数据库。

### 4 · 和第 45 条的关系

**取代它。** 第 45 条把校准值放在扇区最后 8 个槽、靠 `journal_reclaim()` 搬运；
本票改成**放最前面固定地址**，且只有「metadata 区满」这一种情况才需要搬。
第 45 条已在 2026-09-21 标注重开。

## 引出了什么新的未知

两条，都还不够清楚，留在图的 `## Not yet specified`：

- 校准值区那 8 KiB 内部怎么组织（magic / 长度 / CRC / 放几条 / 怎么判「还没写过」）
- 工装按 UID 存副本的形态（存哪、什么格式、谁读）—— 可能整个属于产测那条线
