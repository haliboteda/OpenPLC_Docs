# 五条路径里「测安全性」各指什么

Type: grilling
Opened: 2026-09-20
Status: resolved
Blocked by: -

## Question

用户 2026-09-19 给的五条路径，每条都带着「**并且，测试安全性**」。但五条路径处在**不同的信任状态**，
所以「安全」在每条里指的不是同一件事，得一条条说清。

初步看，每条路径该配的反向用例不一样：

| 路径 | 板子这时信谁 | 「安全」在这条路径里可能指什么 |
|---|---|---|
| ① 直接烧自己的程序 | **公开根**（不设防） | ⚠️ 这条**几乎没有安全性可测** —— 出厂根私钥在开源仓库里，谁都能签。能测的只有「公开根告警确实每次启动都出现」 |
| ② 认领后烧 | 客户自己的根 | 没按 BOOT0 认领被拒；别的密钥签的固件被拒；无签名的高 generation 记录夺不走板子 |
| ③ 换根（`rotate_keys.sh`）、重烧 bootloader | 客户自己编译进去的根 | 公开根告警**不再出现**；旧根签的固件装不进去 |
| ④ 发叶证书 | 同 ③ | 证书不是这块板的根签的 → 拒；证书覆盖的是别人的密钥 → 拒；**真板子收下委托证书并据此执行固件** |
| ⑤ 作废 / 更换叶证书 | 换根之后的新根 | 旧叶签的固件**下次启动被拒**；旧叶再上传被拒；新叶能传能起 |

要定的是：**每条路径到底配哪几条反向用例，以及每条的判据**。

⚠️ **反向用例必须配正向对照。** 「板子应该拒绝」没有对照就分不清「拒绝了」和「板子死了」——
2026-09-17 实测时对照组失败过一次，脚本正确地报了「这一轮什么都没证明」。

## 怎么算答完

五条路径各有一张表：**测什么 · 判据 · 跑法 · 这条测不到什么**，判据要能判真假。

并且明确写下路径 ① 的结论 —— **如果它确实没有安全性可测，就直说**，
不要为了五条对称而编出一条。（出厂态不设防是产品定位的直接推论，不是缺陷。）

## Answer

2026-09-20 定。**五条路径各自的安全性判据如下，复用 13 条现有用例、新增 7 条。**（复用数 2026-09-20 由 10 改为 13，见下面的全集对账）

三个贯穿全表的原则：

- **反向用例必须配正向对照** —— 「板子应该拒绝」没有对照就分不清「拒绝了」和「板子死了」
- **判据不能只看一行日志没出现** —— 日志没抓到也是 0 行，和「没打印」分不开
- **「几乎没有安全性可测」也是结论**，不为对称硬编

### 路径 ① 什么都不改，直接烧自己的程序

板子信**公开根**，私钥在开源仓库里 —— **谁都能签**。

> **这条路径按设计就不设防，所以几乎没有「板子安全」可测。** 这不是缺陷，是产品定位的直接推论
> （客户要能签自己的 sketch ⇒ 出厂根私钥必须公开）。硬编一条会让人误以为出厂态是安全的。

| | 测什么 | 判据 | 用例 |
|---|---|---|---|
| ①-a | **公开根告警是常驻的，不是一次性提示** | **连续复位 3 次**，每次日志都有 `trusts the PUBLISHED root key` | 🆕 `T2-08` |
| ①-b | 验签这条路真的在跑 | 随机密钥签的镜像 → 被拒，**且 app 区一字节没动** | ✅ `T1-11` + `T1-14` |

⚠️ ①-a 要连续三次：**告警的全部价值在于它不消失**。一次性提示会训练用户忽略它，规则就废了。

### 路径 ② 认领后烧

| | 测什么 | 判据 | 用例 |
|---|---|---|---|
| ②-a | 没按 BOOT0 认领被拒 | 回 `Refused`，`getpubkey` **一字节不变** | ✅ `T2-02` |
| ②-b | 认领成功且告警消失 | `takeown` 回 `OK` + 复位后仍认得 + 告警**不再出现** | ✅ `T2-01` |
| ②-c | 别人的密钥签不进来 | 格式正确但签方不对 → 被拒 | ✅ `T1-12` |
| ②-d | 无签名的高 generation 记录夺不走板子 | 扫描器看得见那条记录，但 `getpubkey` 仍返回原主人 | ✅ `T2-04` |
| ②-e | **认领让路径 ① 装的 app 失效** | 认领后复位，板子**拒绝启动旧 app**、停在 bootloader | 🆕 `T2-09` |

⚠️ **②-e 必须有**：认领之后板子不跑原来的程序了，**客户一定会撞上**。没有用例说明这是设计如此，
第一个遇到的人会当成 bug 报上来。

### 路径 ③ 换根（`rotate_keys.sh`）、重烧 bootloader

| | 测什么 | 判据 | 用例 |
|---|---|---|---|
| ③-a | 换根后告警不再出现 | **两件事同时看见**：`Owner slot: empty` **在**，告警**不在** | ✅ `T2-07` |
| ③-b | 旧根（公开根）签的固件装不进去 | 上传被拒 | 🆕 `T2-10` |
| ③-c | 新根签的固件能装能起 | 上传成功 + 复位后正常启动 | ✅ `T2-07` 后半 |

⚠️ **`T2-06`（公开根指纹常量）在这条路径里必然失败**，见
[路径三换根之后 T2-06 必然失败，算不算](E2E-05-is-t2-06-failing-after-rotate-expected.md)。

### 路径 ④ 发叶证书（**不重烧 bootloader**，发证全程不碰板子）

| | 测什么 | 判据 | 用例 |
|---|---|---|---|
| ④-a | 证书的签发根不是这块板的 → 拒 | 工具报 `was not issued by this board's root` | ✅ `T1-18e`（**假板子**） |
| ④-b | 证书覆盖的是别人的密钥 → 拒 | 工具报 `was issued for a different key` | ✅ `T1-18f`（**假板子**） |
| ④-0 | **正向对照**：委托证书由这块板的根签发 → 工具放行 | 工具报 `Certificate was issued by this board's root` | ✅ `T1-18d`（**假板子**） |
| ④-c | **真板子收下委托证书并据此执行固件** | 同事用叶私钥 + 根签发的证书上传 → 成功 + 复位后正常启动 | 🆕 `T2-11` |

⚠️ **④-a / ④-b 测的是「工具的判断」，不是「板子的判断」** —— 它们跑在假板子上。
**④-c 才是这条路径真正的判据**，而它今天只有手工步骤、没有编号也没有退出码。

### 路径 ⑤ 作废 / 更换叶证书（**今天 = 换根，全量作废**）

| | 测什么 | 判据 | 用例 |
|---|---|---|---|
| ⑤-a | 坏签名的换根被拒 | 回 `Refused`，**什么都没变** | ✅ `T2-03` 负向 |
| ⑤-b | 正确签名的换根成功 | 回 `OK` 且 generation +1 | ✅ `T2-03` 正向 |
| ⑤-c | **换根后旧叶签的 app 下次启动被拒** | 复位 → `App signature invalid or absent` → 停在 bootloader | 🆕 `T2-12` |
| ⑤-d | 旧叶再上传 → 被拒 | 上传失败 | 🆕 `T2-13` |
| ⑤-e | 新根签发的新叶 → 能传能起 | 上传成功 + 正常启动 | 🆕 `T2-14` |

⚠️ **⑤-c 是这条路径的核心** ——「作废」这个词的全部含义就是它，而今天它只在 PC 侧证明过。

### ⚠️ 2026-09-20 全集对账补进来的三条

关本图最后一张票之前重跑全集命令，发现上表漏引三条：

| 漏的 | 为什么该有 |
|---|---|
| `T1-18d`（委托证书由本板的根签发 → 工具放行） | ⚠️ **上表只引了 `T1-18e`/`T1-18f` 两条反向，没有正向对照** —— 这违反本票自己定的第一条原则。已补成 `④-0` |
| `T1-23`（一次真实上传走完，且擦除在验证之后） | **五条路径每一条都在传固件**，走的就是它那条路 |
| `T1-13`（启动时重新验签：直接改坏已装好的 app，下次启动必须拒绝） | `②-e` 和 `⑤-c` 都靠「启动时重验」这条机制。`T1-13` 是它的直接测试，作为**前提**引用 |

### 那三条盲区：补成正式用例，不留手工步骤

用户 2026-09-20 选**甲**。`T2-11`（真板子收委托证书）、`T2-12`（换根后旧 app 被拒）、
`T2-13`（旧叶再上传被拒）**给编号、写脚本、接退出码**。

理由是「先标成手工步骤、脚本以后再说」已经被证明会丢：委托证书那份手工步骤写在
`HOW-TO-RUN-TESTS.md` 里好几个月，**因为没编号没退出码，今天没人说得出它跑没跑过**。
