# 过渡期怎么走

Type: grilling
Opened: 2026-09-17
Status: resolved
Blocked by: DR-05

## Question

编号重排会同时动 54 条需求号、全部测试用例号、三张验收单、
以及约 15 个文件里的引用（**含源码注释**，见地图 `## 全集` 的命令 1）。

两种走法：

| | 做什么 | 风险 |
|---|---|---|
| **一次切干净** | 所有引用同一批改完，旧编号当天作废 | 改漏一处就是断链，而 P9 只查路径不查编号 —— **没有任何检查会抓到漏改的编号** |
| **新旧并存一段** | 新文档用新号，旧文档保留旧号，靠 `ID-MIGRATION.md` 对照 | 两套编号同时活着，正是这次重排要消灭的东西 |

要定的还有：**切换期间 `git` 怎么走** —— 一个大提交，还是按模块分批提交。
用户自己手动推，所以分批的话他要推很多次。

## 怎么算答完

写下走哪条路、分几批、每批的边界是什么。
并且回答：**用什么办法发现「漏改的编号」** —— 这是一次切干净的唯一真风险，
P9（路径必须存在）抓不到它。

## Answer

2026-09-17 定。

**走哪条路：一次切干净。** 所有引用同一批改完，旧编号当天作废，不走「新旧并存」。
理由不是偏好，是今天刚付过的代价：13 个测试号改完之后，`ID-MAP.md` 不得不加一条
「这张表现在是混的」——**两套编号同时活着，正是这次重排要消灭的东西**。

**分几批：一批，一个大提交，边界就是「全部改完」。**
⚠️ **这一条是按理解执行的，用户没有明说过，可以否掉。** 判断依据两条：
编号体系改一半没有任何一个中间点是自洽的（上一段那个「表是混的」就是证据）；
以及用户自己手动推，分批等于让他推很多次。

**怎么发现漏改的编号**：`$TOOL:TestCase/tools/check_no_stale_ids.py`，已经写好。

| | |
|---|---|
| 输入 | **以 [DR-02-id-mapping.md](../DR-02-id-mapping.md) 为唯一输入**，从「旧编号」列解析出要找的 id。代码里一个 id 都没硬编码 —— **往对照表加一条重命名，它自动被监督** |
| 找几个 | 实测解析出 **52 个**。`C6` 这个编号本来就不存在；`C13` `C14` 进 DEFERRED 不重排，在对照表里住另一节、表头形状不同，解析器正确地不收它们 |
| 现在跑什么结果 | **全红，52 个全部命中** —— 因为重排还没做。**这不是它坏了** |
| 所以 | **暂不进 `selfcheck`，重排完成后再挂进去。** 这一点必须写明，否则下一个人会以为它是坏的 |
| 白名单 | `ALLOW` 只有三类，各有理由：`sha256.c` / `sha256_ref.py` / `sha256.h`（SHA-256 的工作变量真的叫 `T1` `T2` `S1`）、`DR-02-id-mapping.md`、`ID-MAP.md` / `ID-MIGRATION.md`（**它们就是用来引用旧编号的**） |

⚠️ **这条检查是一次切干净唯一的兜底。** `P7` 只比对两份名单**彼此**一致、
`P9` 只查路径能不能 resolve —— **散落在文档正文和源码注释里的旧编号，两者都看不见**。
今天改 13 个编号时是靠人从 41 个候选里一个个排掉 20 个误报做完的，完整重排的量是它的四五倍。
