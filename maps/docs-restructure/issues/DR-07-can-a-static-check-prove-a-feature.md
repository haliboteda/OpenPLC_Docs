# 静态检查能不能当功能需求的证据

Type: grilling
Opened: 2026-09-17
Status: resolved
Blocked by: -

## Question

**四条**功能需求的唯一证据是静态检查（`P2` 跨仓镜像没分叉，`P4` 变体头自洽）：

| 新编号 | 要做到什么 |
|---|---|
| `R1-06` | app 请求进上传模式的通道只有一条（SRAM4 `boot_handoff_t`） |
| `R1-07` | 同一台主机上的多个工具不会互相打断上传 |
| `R1-14` | 每块板的 MAC 互不相同（从 UID 派生） |
| `R3-04` | FMC 占用的 39 个脚在变体头里**有名字、看得见**，用户不会误碰（证据是 **P4 + P2**） |

**矛盾在于**：按这张图定的划分标准，`P1`–`P12` 这些静态检查属于**工程约束、不给模块号、
不进功能表**。于是这三条功能需求的证据落在功能表之外那一层。

而且 P2 查的**不是这条功能本身** —— 它查的是「同一份代码在两个仓库里没有分叉」。
`R1-14` 尤其明显：P2 只能证明 MAC 派生算法两边写得一样，
**证明不了两块板算出来的 MAC 真的不同**（那要第二块板，`R1-14` 因此是 🟡）。

要定的是：**一条功能需求的「谁证明」栏里，允不允许出现工程约束层的检查号？**
不允许的话这三条写什么。

## 怎么算答完

三条各自的「谁证明」栏有一个明确写法，且这个写法**不制造第二套规矩** ——
能套用到将来任何一条「只有静态检查撑着」的功能需求上。

## Answer

2026-09-17 定。

**判据一句话：一个检查能不能当某条需求的证据，看它测的是不是这条需求本身，
不看它是静态还是动态。**

这条判据不制造第二套规矩，而且它同时解释了为什么有些「只有静态检查」的需求反而该保持 ✅：

| 需求 | 它的静态检查测的是什么 | 差在哪 | 结论 |
|---|---|---|---|
| `ENG-02`（`D7` 版本三处一致） | `P1` 查版本三处一致 | **没有差** | ✅ 名副其实 |
| `ENG-03`（`D8` 跨仓镜像不分叉） | `P2` 查跨仓镜像不分叉 | **没有差** | ✅ |
| `ENG-04`（`D9` core live 进了 git） | `P3` 查的就是这件事 | **没有差** | ✅ |
| `ENG-06`（`F1` 一条命令跑完检查） | `P7 P8 P9 P11` 就是那些检查 | **没有差** | ✅ |
| `R1-06`（通道只有一条） | `P2` 查两边代码没分叉 | 分叉与否 ≠ 只有一条 | **降 🟡** |
| `R1-07`（多工具不互相打断） | `P2` 查锁的常量两边一致 | 一致 ≠ 真不打断 | **降 🟡** |
| `R1-14`（每块板 MAC 不同） | `P2` 查算法两边一样 | 算法一样 ≠ 两块板真的不同 | 保持 🟡 |
| `R2-01`（客户能把自己的根编进去） | `P2` 比对三份副本 | 副本一致 ≠ 换根这条路走得通 | 保持 🟡 |
| `R3-04`（FMC 脚看得见） | `P4` 查表自洽、`P2` 查不分叉 | 表对 ≠ 用户不会误碰 | **降 🟡** |
