# 模块文档的骨架长什么样

Type: prototype
Opened: 2026-09-17
Status: resolved
Blocked by: -

## Question

四份模块文档要长成同一个样子，否则「统一标准」只停在划分上，落到纸面又乱了。

先做 **M1 固件升级** 一份样张给用户看，定下来之后照抄到另外三个模块。要定的是**顺序和成分**：

- 开头放什么 —— 一句话说清这个模块让外面的人能做什么？还是先放流程图？
- **流程图放几张、放在哪**（Mermaid）。M1 至少有「一次上传的八步」和「启动决策链」两张
- 功能表长什么样 —— 一行一条需求，列有哪些
- 需求和测试**同表还是分表**。用户要求「区分需求和测试」，但没定是分两张表还是同一张表两列
- 判据、证据日期、证据还成立吗 —— 这几列现在在 `STATUS.md` 里，要不要跟着搬进模块文档
- 模块之间互相引用怎么写（M1 要提到 M2 的信任根）

⚠️ **样张要真能用**，不是排版示意 —— 用 M1 的真实需求和真实流程填，
用户看着它就能判断「照这个做完四个模块，我读起来顺不顺」。

## 怎么算答完

`docs/modules/` 下有一份 M1 的完整样张，用户看过并明确说「照这个做」。
样张里的 Mermaid 图在 VSCode 预览里渲染得出来，
且样张自己通过 `python tools/check_doc_paths.py`（P9，路径不许断链）。

## Answer

2026-09-17 定。骨架的样子在 [../../../docs/modules/M1-firmware-upgrade.md](../../../docs/modules/M1-firmware-upgrade.md)，这里只记定了什么。

**六节的顺序**：① 这个模块让外面的人能做什么 + 管到哪为止 → ② 主流程图（Mermaid）
→ ③ 功能表 → ④ 测试怎么跑 → ⑤ 为什么不记证据日期 → ⑥ 边界与和别的模块的关系。

**三处写法，用户 2026-09-17 拍板**：

| 定了什么 | 结论 |
|---|---|
| 功能表 | **需求和测试同一张表**，一行一条，加一列「阶段」体现流程顺序。判据和跑法不挤进来 |
| 测试详情 | **一张大表**（# / 测什么 / 判据 / 跑法 / 状态），要展开解释的写成表格下面的脚注，不为它拆小节 |
| 证据列 | **只留 ✅/🟡/⬜ 一个状态**。日期和「最近一次跑出来多少」不进文档 —— 每跑一次就变的数据用文档维护会漂，且漂时无人报警 |

**流程图照源码画，不照现有文档画**：启动决策链取自 `$BOOT/IAPServer/IAP_server.c` 的 `server_decide()`。

**顺带纠正两个数**：M1 粗分进来的需求是 **32 条**（不是 34，原先多算了 2）；
填表时发现**九条需求的「谁证明」不是测试用例**（七条手工、一条代码审查、三条只有静态检查）——
定稿里逐条写出来了，因为不写就会被当成有测试覆盖。

⚠️ **和「怎么算答完」的偏差，写明在这里**：判据原文要求样张落在 `docs/modules/`，
**实际留在 `maps/docs-restructure/`**。理由是单独建一份 M1，它引用 M2 / M3 的地方会被 P9 判成断链
（实测触发 4 处）。判据的实质 —— 骨架定下来、用户拍了板、P9 过 —— 都满足了。
另外用户拍板的是那三处写法，**填满到 32 条之后的定稿他还没逐行看过**。
