# 按功能模块重做文档与编号

## Destination

`docs/` 重组成**一份自顶向下、按功能模块划分的设计文档**：**`docs/tables/STATUS.md` 演化成那个入口**，装 12 行全局汇总 + 模块索引 + 场景索引表，
每个模块一份，事实只在它所属模块里写一次。需求编号 `R<模块号>-<序号>`、
测试编号 `T<模块号>-<序号>` 全部重排到位，旧号能通过对照表查回来，`selfcheck` 全过。

**走到终点的样子**：打开入口文件，能看到四个模块和它们的功能表；
点进任一模块，能看到它的流程图（Mermaid）、需求、测试，**不需要再跳到第二个地方**。

## 全集

**这张图要找的是「所有会被重编号或重组织的东西」。** 两条命令，各管一半：

```bash
# 1. 还写着旧编号的文件 —— 以 DR-02-id-mapping.md 为唯一输入，零硬编码
python IAPTranfer_Tool/TestCase/tools/check_no_stale_ids.py

# 2. docs/ 下的每一个文件 —— 每一份都要有去处
find OpenPLC_Docs/docs -type f
```

**对账方式**：命令 1 **退出码 0** 才算编号改全了；命令 2 的每个文件都在 `DR-05` 的去处清单里。

⚠️ **命令 1 在重排完成之前必然全红**（52 个旧编号都还在），那是预期不是缺陷。

⚠️ **这条命令换过一次。** 原来写的是一条 `grep`，里面有 `case` 这个词 ——
**`case` 是 C 的关键字**，`case A1:` 这类 switch 语句被大量误配：
限定到产品六仓仍报 121 个文件，其中 `ref`（参考工程，不该动）就占 30 个。
2026-09-17 关最后一张票前按约定重跑对账时抓到，**抓到的不是漏干的活，是命令本身**。

**基线**（2026-09-17）：命令 2 = 33 个文件（32 `.md` + 1 `.html`），`DR-05` 逐份点名 33 份，对得上。
