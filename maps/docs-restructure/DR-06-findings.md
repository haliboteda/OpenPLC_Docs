## 结论先说：困难不在硬件，在「没人把判定接到退出码上」

**这十条里没有一条卡在「驱动不了硬件」。** 真板子该做的事，现有脚本几乎都做得了：
烧写走出货的 `IAPTool`、串口日志有 12 个脚本会读（`open_log_ports` / `read_log_ports`，
定义在 `$TOOL:TestCase/tools/common.py`）。

**卡住的是最后一步：判定结果没有变成退出码。**

最典型的是 `$TOOL:TestCase/tools/upload_and_watch.py` —— 它已经跑完整的真实上传、抓串口、
逐条核对 SDRAM 暂存该有的行为（`verdict()` 函数，第 23–50 行），**然后 `main()` 无条件 `return 0`**。
因为 `common.py:124` 的 `Fail()` 只是把字符染成红色打印出来，**不改变任何状态**。

所以它是一个**观察工具**：人看着彩色输出自己判断。**它不是用例，因为它永远"通过"。**

这个分界可以量出来：

| 脚本 | 失败退出路径条数 | 是不是登记过的用例 |
|---|---|---|
| `run_m5.py` | 14 | 是（诊断串口不被 sketch 掐掉） |
| `run_takeown.py` | 11 | 是（认领板子） |
| `run_au1.py` | 9 | 是（nonce 跨掉电不重复） |
| `run_s3.py` / `run_s4.py` | 各 8 | 是（启动验签 / 掉电恢复） |
| `run_sdram.py` | 7 | 是（SDRAM 封装） |
| **`upload_and_watch.py`** | **2** | **否** —— 而且那 2 条是参数校验（没给 `--ip`、找不到镜像），不是判定 |

> **所以用户的直觉是对的：确实"已经做到了一些现在标手工的东西"，只是做到了「跑完并打印」，没做到「判定并报告」。**

### 🟡 差一点 —— 零件都在，要写几十行胶水（4 条）

#### R1-22（旧 `C1`）· 镜像先过 CRC32

| | |
|---|---|
| **判据** | 发一个**故意错的 CRC**，板子必须打 `Checksum FAIL. Expected: ... , Got: ...` 并回 `Checksum Failed`（`IAP_server.c:395-397`） |
| **现有覆盖** | **发得出来**：`$TOOL:TestCase/signature.go:129-130` 自己用 `crc32.ChecksumIEEE` 算校验和、自己拼 `flash <size> <crc32hex> <sig>` 命令。出货的 `IAPTool` 做不出坏 CRC，但这个 Go 用例是原始 TCP，能 |
| **差什么** | 照 `signature.go` 复制一份，把 checksum 改成错值，判板子的回复。约 30 行 |
| **要人吗** | 不要 |

⚠️ **正向（CRC 对）测不出东西** —— CRC 通过时不打任何日志，直接往下走。这条只有负向用例有意义。

#### R1-05（旧 `A5`）· 从 CDC 请求进上传模式时不启动以太网

| | |
|---|---|
| **判据** | `Core/Src/main.c:413-414`：`MX_LWIP_Init()` **只在** `IAP_ETHERNET` 或 `IAP_ALL` 模式下调用。所以 CDC 模式时 lwIP 根本没初始化 |
| **怎么从 PC 观察** | 把板子弄进 **CDC 上传模式**，然后广播 UDP 发现 —— **板子必须不应答**。应答了就说明以太网起来了 |
| **现有覆盖** | 两头的零件都在：`tools/enter_bootloader.py` 能把板子留在 bootloader，`udp_discovery.go` 会发那四个发现关键词 |
| **差什么** | 把两者串起来，并确认「怎么只请求 CDC 模式」这一步。约 40 行 |
| **要人吗** | 不要 |

> **这条是个反向用例**（判据是"什么都没发生"），所以**必须同时验证正向对照** ——
> 以太网模式下同样广播必须**有**应答。否则板子死了也会"通过"。

#### R1-29（旧 `D2`）· journal 扇区满了能 reclaim 并恢复

| | |
|---|---|
| **判据** | 串口打印 `Reclaiming state sector (<丢弃数> slots discarded)`（`bootloader_state.c:316`）。满之前还会打 `** Journal full - new events are not being recorded.`（第 159 行） |
| **现有覆盖** | 判据可读，但**没有工具能把 journal 填满** |
| **差什么** | 要么反复上传几十次把槽用完（慢但真实），要么写一个直接往状态扇区灌记录的工具 —— `tools/inject_owner_record.py` 是同类操作的现成范例。约 80 行 |
| **要人吗** | 不要 |

#### R1-13（旧 `B11`）· 设备定位靠 UDP 广播 + UID 匹配，不依赖 MAC 一致

| | |
|---|---|
| **判据** | 发现应答的格式是 `<设备名>_<UID 十六进制>_<角色>_<版本>`（`IAP_server.c:167-169` 的 `iap_identity_string()`），PC 工具按 `_` 切开解析。**UID 本来就在每一条发现应答里** |
| **现有覆盖** | **正向那一半好做**：`udp_discovery.go` 已经在收这些应答，只是没断言 UID 字段 |
| **差什么** | **难的是「不依赖 MAC 一致」那一半** —— 要证明它，得烧一个自己改了 MAC 的 app 上去，再看还找不找得到。那是一次完整的烧写流程，不是一个断言 |
| **要人吗** | 不要，但要准备一个改过 MAC 的测试 app |

### 🔴 本质上要人在场（3 条）

#### R1-04（旧 `A4`）· 按住 BOOT0 复位能强制进入上传模式

**判据很干净**：串口打 `** UPLOAD Mod ... (BOOT0 held)`（`IAP_server.c` 的 `server_decide()`，
`reason = "BOOT0 held"` + 第 602 行的 `printf`）。

**但要人按住按钮穿过启动继电器窗口。** 这是物理动作，除非接一个继电器去拉 BOOT0 引脚，
否则自动化不了。**判定那一半是现成的**（抓那行日志），只有触发那一半要人。

#### R1-30（旧 `D3`）· 复位原因能正确报出（PIN / SOFT / POR）

判据：`Core/Src/main.c:368` 打 `** Reset cause: <原因>`，
取值来自 `IAP_boot_handoff.c:96` 的 `boot_handoff_reset_cause_str()`：
`WWDG` `IWDG` `SOFT` `POR` `PIN` `BOR` `D2RST` `UNKNOWN`。

**三种要分开看，不是一个整体**：

| 要测哪种 | 怎么触发 | 能自动吗 |
|---|---|---|
| `SOFT`（软件复位） | `IAPTool` 的认证重启命令 | 🟢 **能** |
| `PIN`（复位键） | 按板子上的复位键，或外部拉 NRST | 🔴 要人 |
| `POR`（上电复位） | 真断电再上电 | 🔴 要人（和掉电那三条用例一样） |

**所以这条严格说是 1/3 能自动。** 把它整条标成"手工"掩盖了这一点。

#### R1-31（旧 `D5`）· RTC 备份域失效（VBAT 没电）时能被发现

判据是三选一，`IAPServer/iap_auth.c:149 / 158 / 162`：

- `Backup domain retained, nonce counter = <n>` —— 正常
- `** Backup domain witness missing, but nonce counter = <n>. **` —— 见证丢了但计数器还在
- `** Backup domain was lost - RTC battery absent or empty. **` —— 真的掉了

**要触发第三种必须把 RTC 电池拆掉或放空。** 没有软件办法。

⚠️ `STATUS.md` 这条的备注记着一件比表象重要的事：真正的缺陷是
**bootloader 的见证和 app 的 nonce 计数器曾经撞在同一个备份寄存器上**，
导致 app 每次从 bootloader 回来都重发同一串 nonce。那个已修。

## 汇总

| 类别 | 条数 | 哪些 |
|---|---|---|
| 🟢 只差把判定接到退出码 | **3** | R1-01 CDC 烧写 · R1-03 以太网烧运行中的板 · R1-28 journal 槽数 |
| 🟡 零件都在，差几十行胶水 | **4** | R1-22 CRC32 负向 · R1-05 CDC 不启以太网 · R1-29 journal 回收 · R1-13 UID 定位 |
| 🔴 要人在场 | **3** | R1-04 按住 BOOT0 · R1-30 复位原因（**其中 SOFT 那种能自动**）· R1-31 拆 RTC 电池 |

**十条里七条能做到全自动，另外三条中有一条（复位原因）能自动化掉三分之一。**

⚠️ **要人在场不等于没法当用例。** 已有三条用例就是这样跑的
（`run_s4.py` 的两条掉电用例、`run_au1.py` 的 nonce 用例）：
**脚本靠板子停止应答来判断电真的断了，人只要动手，不用回来按回车。**
R1-04（按 BOOT0）和 R1-31（拆电池）可以照这个办法写。
