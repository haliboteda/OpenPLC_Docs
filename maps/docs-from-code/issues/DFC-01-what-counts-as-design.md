初步观察到的几类，等着被判：

|---|---|

搬走它可能正确，也可能等于把地雷的标记撕了。

## 进行中的发现（2026-09-16，票还没关）

**用户给了判据**（原话）：

> 「只要是结论性的都可以留在注释里，我要精简的是那种**描述修改过程、描述为什么、原因是什么**那种。」

在五处真注释上试过，切得动（例子见 [../TODO-PLAN.md](../TODO-PLAN.md)）。

⚠️ **但读到语料里最大的那一段（`TestCase/CAN/can_test.h`，223 行）时，两分法不够了。**

那 223 行几乎全是**硬件事实**：引脚表、BGA ball 号、收发器型号（ISO1044BDR）、
隔离电源（U7 装在背面）、端子映射、JP7 出厂开路、R83/R84 DNP、以及一条
「Klemmblockzuordnung.pdf 第 4 页从端子 09 起是错的」的陷阱。

它既不是「这段代码要达成什么」，也不是「为什么这么设计」，而是**从原理图/网表抄过来的一份拷贝**。

按 `结论 / 为什么` 两分，这 223 行会被判成「结论，留下」—— **那是错的**：

- `verify-dont-assume` 规矩写着：**固件、core、变体头都是抄件，不能当唯一出处**
- `REFERENCE-LAYER-TAXONOMY` 写着 `hardware/` 的**出处只能是原理图 / 网表 / 数据手册**
- `docs/hardware/HARDWARE-FACTS.md:289` 已经记着那条 C09/C10 陷阱，并点名它**当时还住在固件两处** ——
  也就是说这份重复是已知的，只是没人去收

**所以判据要三分，不是两分**：

| 类 | 去哪 |
|---|---|
| 结论 + 一句话为什么 | **留在注释里** |
| 成段的论证、权衡、修改经过 | **搬进设计文档** |
| **硬件事实的拷贝**（引脚、型号、端子、跳线状态） | **搬进 `docs/hardware/`，注释里只留一条指针** —— 它的权威出处是原理图，固件本来就只是抄件 |
