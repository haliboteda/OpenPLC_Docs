# 把设计、需求、测试从代码注释里提出来

## Destination

**文档是最全最准的那一份；代码注释和它同步。**

⚠️ **2026-09-16 用户改过一次终点，改小了**：原来是「把设计从注释里搬出来，注释只说这段代码要达成什么」，
现在是 —— **现有注释的内容可以不动**，用它去**比对并补全文档**，然后让两边同步。

> 用户原话：「现有注释里面的内容可以不动，分模块把这些注释里面的东西跟设计、需求等文档比对，
> **保证文档是最全最准的**，注释都跟文档同步。」

所以这张图**不再是一次搬迁**，是一次**比对补全**：注释是原料，文档是产物，注释留在原地。

## Not yet specified

- **P9 不查 `#锚点`** —— 2026-09-16 撞见一条：`PORTTOOL-FLOW.md` 的链接写着「全部 9 条命令」，
  标题早就是「全部 8 条命令」。**目标文件存在，所以 P9 全绿。**
  临时脚本扫了 77 份文档报 14 处，**其中 13 处是它自己把 `—` `；` `✅` 算错了的误报** ——
  要做成常设检查，得先把 GitHub 的 slug 规则抄准，否则又是一条「看起来在保护、其实没有」的检查

- **批 3–5 靠信号词筛，不是逐行读** —— 信号词漏掉的段落会被记成「0 段」，和真的没有可搬的长得一样

- **P9 不管「指得对不对」** —— 引用可以指到一个存在的文件，而那文件已经不讲那件事了
- **P9 只验链接指得到东西，不验链接文字对不对** —— 这次撞见一条目标对、文字是旧路径的，检查全绿

- **8,611 行怎么读完。** 人力逐行不现实，但全自动提取会把「为什么这么设计」和
  「这一行在干什么」混为一谈。分批的切法、顺序、谁来判，都还没想清楚
- 提出来之后，参考层现有八类够不够 —— 「需求」已有 STATUS、「测试」已有 TEST-CASES，
  「设计」散在 DECISIONS 和各域，三大块和八类不是一一对应
- **精炼去重的判据**。P8 现在豁免代码块；提取之后同一个事实会同时活在注释和文档里，
  那正是 P8 要抓的，但它现在看不见代码
