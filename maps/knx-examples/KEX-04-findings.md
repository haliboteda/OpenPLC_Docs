# 测试脚本能不能经 IP 网关直接收发组报文 —— 现场发现

票：[测试脚本能不能经 IP 网关直接收发组报文](issues/KEX-04-can-the-script-talk-through-the-ip-gateway.md)。票 2026-10-09 已答（测试盒网关）；下面按日期记现场结果。

| 字段 | 值 |
|---|---|
| 名称 | `HDL KNXnet/IP Device`（厂商号 0x0073 = HDL） |

| 物理地址 | 1.1.4 |

| 做了什么 | 结果 |

| 往总线发报文 | 一个没发 |

## 2026-10-09 现场

PC 在 WLAN 192.168.0.32。⚠️ 本机默认路由走一张 sing-tun 虚拟网卡（`tun0`，代理软件建的），不绑源地址的包先进代理。探测脚本在 `$TEST/tools/knx_gateway_probe.py`。

| 做了什么 | 结果 |
|---|---|
| UDP 单播 DESCRIPTION_REQUEST（HPAI 填本机地址 / 填 0 原路回两种；走 `tun0`、绑 WLAN 地址两种） | 都不回 |
| TCP 3671 | 绑 WLAN 地址直连被拒 —— 网关不开 TCP 隧道。走 `tun0` 时「能连上」是代理在本机接的，不算数 |
| ping（绑 WLAN 地址） | 通，3 ms |
| 本机防火墙 | 公用配置文件，挡入站，本地规则不生效（只认组策略）；会话也不是管理员，加放行规则这条路走不通 |

结论：从 WLAN 这一侧走不通 UDP 隧道；是网关只认同网段，还是防火墙挡了回包，**分不清，也不再在这台 PC 的 WLAN 上查**。ETS 历史上用的是有线口 10.32.2.199，同网段直连。

## 2026-10-09 测试盒网关（同网段）

用户的 KNX 测试盒带一个网关，经网线接在 192.168.0.x。`$TEST` `python tools/knx_gateway_probe.py` 组播搜索自己找到它。

| 做了什么 | 结果 |
|---|---|
| 组播 SEARCH_REQUEST | 192.168.0.30「KNX IP Interface 732 secure」，物理地址 9.0.1，8 个隧道槽 |
| UDP 隧道往 31/7/255 写 0 | 网关确认，作为 9.0.2 |
| 第一条隧道开着时再开第二条 | 成功，作为 9.0.3 —— ETS 和脚本可以同时连 |
| 读 15.15.255（板子出厂物理地址）的设备描述符 | 没有 ACK：板子不在这条总线上，或总线没电，待用户确认接线 |

> 结论：测试脚本经这个网关收发组报文走得通，不用换到 10.32.2.x。

## 2026-10-10 测试盒网关

| 做了什么 | 结果 |
|---|---|
| ETS5 开着**总线监视器**时开 UDP 隧道 | 网关拒绝，`E_TUNNELLING_LAYER`；ETS 切成**组监视器**后脚本连上 9.0.3、9.0.4 |
| 板子（`KNX_BusMonitor`）经 USB 发 `w 31/7/255 1` | 板子报 `not acknowledged`，隧道上没收到 |
| 隧道往 31/7/254 写 1 | 板子没打印 |
| 量板子 KNX 端子 | 29.5 V；PH12 = 1 |
| 不经 KNX 库的探针轮询 PA10（DWT 计时），隧道同时发报文 | 没有约 35 µs 的低脉冲；只有约 100 个 / 秒、宽度不到 1 µs 的毛刺，有无报文都一样 |
| ST-Link 换烧工装 0.10.0（09-09 跑通过的同一套 KNX 代码），COM12 `pt.start knx mode=frames` 15 秒；之前整片 flash 已备份，测完写回并逐字节核对 | 发 16 帧，隧道一帧没收到；RX 817 个脉冲、`w_avg=208`（应约 35 µs）、725 个字符 700 个坏、收到的全是 `FF…` |
| 隧道对 9.0.2、9.0.10、9.0.11 做地址检查 | 都应答，总线本身正常 |
| 不经 KNX 库的探针在 PB14 上打 35 / 20 / 50 / 100 µs 脉冲（最长连续约 2 ms），同时轮询 PA10 | PA10 一个脉冲都没回来；09-09 同一条环回是通的 |

> 结论：脚本跑着时 ETS 只能开组监视器。09-09 跑通过的工装固件在这块板上同样收发都不通，所以是这块板的 KNX 硬件坏了，不是 Arduino KNX 库的问题；坏在哪个器件见 [KEX-08](issues/KEX-08-board-sees-no-bus-pulses.md)。

## 2026-10-12 测试盒上已有的配置

测试盒的设备早已有人用 ETS 编程过，本机没有那份工程。下表是用 ETS Device Info 读出来的，加上板子 `KNX_BusMonitor` 在总线上看到的。

| 设备 | 物理地址 | 组地址 | 怎么核实的 |
|---|---|---|---|
| 开关执行器（ETS 读到的厂家是 Lingg & Janke，程序是 2207 V1.0，掩码 0012） | 9.0.10 | 1/0/1 开关（可写）、7/3/1 状态（发送） | Device Info；板子发 `w 1/0/1 1` 和 `w 1/0/1 0`，用户看到 A1 的红灯跟着亮、灭 |
| 温度传感器 | 9.0.12 | 每 5 秒往 7/5/4 写一次温度（DPT 9.001） | 板子监视 |
| IP 接口 732 secure | 9.0.1 | — | 见上文「2026-10-09」 |

同日板子换成 `KNX_Temperature`、用户在 ETS 里下载（对象 21→7/5/4、22→1/0/1）后，又经网口在 app 运行中升级两次（不按键）。之后用户在 COM12 看到温度持续打印；输入 `t 20` 时 A1 和 DO2 都开，`t 30` 时都关。`run_knx_box.py` 的 `T3-18` 脚本本身没跑过。

去掉 `OpenPLC_KNX` 应用配置块后，ETS 把板子地址改成 1.1.20 再下载，经网口重传新程序，开机打印 `KNX: address 1.1.20, configured`，温度照常收到：地址和组表都留住了。

> 结论：控制执行器不用重新编程，往 1/0/1 写就行；板子写 1/0/1 时执行器没有往 7/3/1 回报状态（只在按手动键时回报）。
