代码在 `IAPServer/bootloader_state.{c,h}`，判定链在 `IAPServer/IAP_server.c` 的 `server_decide()`。

## 它为什么存在

Bootloader 不能靠看 app 的头几个字节猜「这像不像一个合法程序」。旧版本就是这么干的 —— 看第一个字（MSP）像不像一个合理的 RAM 地址 —— **只要 flash 里恰好有个看着像栈指针的值，损坏的或被人写进去的镜像一样能通过。**

所以每次成功烧写要留下一份**出生证明**：大小、哈希的依据、签名、证书。下次上电拿它去核对。

⚠️ **所有规则都偏向保住 metadata。** 这个扇区里另一样东西（校准值）跟板子走、不跟固件走，两者的诉求相反 —— 下面的布局就是为了让它们互不干扰。

## 布局

```
0x081E0000  ┌─ 校准值区  8 KiB ─────────────────────────┐
            │  固定地址，不 append                       │
            │  工装经 JLINK 写；固件不提供写入命令        │
0x081E2000  ├─ 根区  8 KiB ─────────────────────────────┤
            │  'O' 段 32 × 160 B：认领 / 换主 / 恢复出厂  │
            │  'R' 段 96 × 32 B：被撤销的叶              │
            │  格式见 M2「记录格式（v4）」                │
0x081E4000  ├─ metadata 区 约 112 KiB ──────────────────┤
            │  append，一条 7 个 flash word = 224 B      │
            │  最后一条生效；3583 格 ÷ 7 = 511 条         │
0x081FFFE0  ├─ 完整标记 32 B ───────────────────────────┤
            │  回收时最后写；开机据此判断扇区是否写完整   │
0x081FFFFF  └────────────────────────────────────────────┘
```

根区从扇区 0 尾部搬来，是为了让换根不限次数、而且从不擦写 bootloader（[M2「根区为什么在扇区 15」](../M2-ownership.md)）。

格子大小 **32 字节 = H7 的一个 flash word**，写入粒度下限，不能再小。

| 类型 | 首字节 | 占几格 | 内容 |
|---|---|---|---|
| `M` metadata | `0x4D` | **7** | `app_size` / `signature` / **整张证书** |
| 空 | `0xFF` | — | 擦除后的 flash |

M 记录占 7 格而不是 4 格，是为了把授权这个镜像的**那张 128 字节证书整条存进去** ——
只缓存叶公钥会让「换 owner 追溯作废固件」这条性质静默失效。

`_Static_assert` 锁死结构体尺寸。**这些尺寸就是 on-flash 格式** —— 多一个 padding 字节
会让已经写进去的每条记录的每个字段全部错位，所以让它编译失败，而不是运行时才发现。

## 校准值区的格式

2026-09-28 定（[校准值区那 8 KiB 里放什么格式](../../../maps/per-board-calibration/issues/CAL-05-what-is-the-layout-of-the-8-kib-area.md)）。
**格式归 `$BOOT/IAPServer/calib_area.h`**，core 和工装照它读写，`P2` 查三边一致（[ARCHITECTURE.md](../../repo/ARCHITECTURE.md) 跨仓镜像第 13 条）。全部小端，从 `0x081E0000` 起：

| 偏移 | 长度 | 字段 | 值 |
|---|---|---|---|
| 0 | 4 | `magic` | `0x4C41434F`（`"OCAL"`） |
| 4 | 2 | `version` | `1` |
| 6 | 2 | `channels` | `4` |
| 8 | 12 | `uid` | 芯片 UID 三个字，w0 w1 w2 |
| 20 | 32 | `ch[4]` | 每路 `float gain` + `float offset`，顺序 AI1、AI2、AO1、AO2 |
| 52 | 4 | `crc32` | 偏移 0–51 的 CRC-32（IEEE 802.3，和 zlib 相同） |

其余字节保持 `0xFF`。

**系数的含义**：`实测 ≈ gain × 板子的标称值 + offset`，和工装的拟合同一个方向（`$PORTTOOL/internal/ptcal`）。单位：AI1 是 mV，AI2、AO1、AO2 是 mA。
输入直接套这条式子；输出要反过来算：要出目标值，写给硬件的是 `(目标 − offset) / gain`。

| 读到的情况 | 判为 | app 怎么做 |
|---|---|---|
| `magic` 不对 | 没写过 | 退回标称换算，打一行日志 |
| `crc32` 不对，或 `version` 不认识 | 写坏了 / 格式不认识 | 同上 |
| `uid` 和本机不同 | 不是这块板的 | 同上 |

## 写入路径

| 路径 | 谁在场 | 多久一次 | 擦什么 | 掉电后果 |
|---|---|---|---|---|
| **工装写校准值** | **人在场** | 出厂 + 偶尔重校 | PC 经 JLINK 读出扇区 15 → 换掉前 8 KiB → 擦整扇区 → 写回（[修正值怎么写进板子](../../../maps/per-board-calibration/issues/CAL-04-how-do-values-get-onto-the-board-and-survive-the-reflash.md)） | 当场重来；PC 上按 UID 留着存档 |
| **升级写 metadata** | 无人值守 | 511 次里的 510 次 | **不擦**，纯 append | 零风险 |
| **认领 / 换主 / 撤销** | 无人值守 | 每次一条 | **不擦**，往根区 append | 最多留一条半写的记录，被忽略 |
| **回收**（三种触发，见下） | 无人值守 | 见下 | 整扇区 | 见「回收时掉电」 |

### 什么时候回收

| 触发 | 多久一次 |
|---|---|
| metadata 区满 | 约每 511 次上传 |
| 根区 `'O'` 段满 | 约每 30 次认领 / 换主 / 恢复出厂 |
| `setowner --wipe` | 用户要求时（清空撤销名额，见 M2） |

### 回收的六步

| 步 | 做什么 |
|---|---|
| ① | 读进 RAM：校准值 8 KiB、当前生效的 owner 记录、全部 `'R'` 记录、最后一条 M 记录 |
| ② | 把 owner 记录、`'R'` 记录、最后一条 M 记录暂存进备份 SRAM，带本板 UID 和 CRC |
| ③ | 擦整个扇区 |
| ④ | 写回：校准值 → 根区（只剩当前那条 owner 记录，`--wipe` 时 `'R'` 段清空）→ M 记录 → 本次要追加的新记录 |
| ⑤ | 最后写完整标记 |
| ⑥ | 清掉备份 SRAM 里的暂存 |

⚠️ **压缩后的 owner 记录不带上一代签名。** 它前面的链已经丢了，带签名写回去下次启动无从验证；
不带签名读起来就是一条首次认领 —— 理由同今天的 `setowner --wipe`（[M2](../M2-ownership.md)「`setowner --wipe`」）。
签名在动第一个字节之前已经验过。

**备份 SRAM 只靠 VBAT 时保持内容，前提是 bootloader 置位 `PWR_CR2.BREN` 并等 `BRRDY`；擦一个扇区典型 1 s、最长 2 s（x64）**，出处见 [ROOT-05-findings.md](../../../maps/root-key-without-bootloader-reflash/ROOT-05-findings.md)。⚠️ 系统复位后是否保持、tamper 是否会擦，手册没直说，要上板验。

### 开机判断

```
完整标记在吗？
  ├─ 在 ─────────────────────────► 正常扫描（见下）
  └─ 不在 ─► 备份 SRAM 暂存有效吗（CRC 对且 UID 是本板）？
              ├─ 有效 ─► 用暂存重做 ③–⑥，再正常扫描
              └─ 无效 ─► 没有根：不跑 app，等下一次上传自动认领
```

刚出厂的板子扇区 15 只有校准值、没有完整标记、暂存为空，走的就是最后一支 —— 这正是决策 72 要的出厂状态。

### 回收时掉电

| 掉电发生在 | 电池正常 | 电池也没电 |
|---|---|---|
| ①–② | 什么都没丢 | 同左 |
| ③–⑤ | 从暂存恢复根区和 M 记录；校准值由工装按 UID 存的副本重写 | **根和 M 记录丢失**：回到没有根，等同恢复出厂，下次上传自动认领、重传固件 |
| ⑥ | 完整标记在，暂存被忽略 | 同左 |

**备份 SRAM 稳压器没就绪（`BRRDY` 不亮）时，回收照做，只打一条警告。**
不就绪就拒绝的话，这块板就再也恢复不了出厂、也换不了主；代价是回收途中掉电时暂存可能丢，后果同上表「电池也没电」那一列（用户 2026-09-30 定）。

⚠️ **校准值在回收窗口里只在 RAM 里**，靠「工装按板子 UID 留一份副本」兜住 ——
把后果从「回产线重新标定」降成「重写一次」。

### 为什么只能在这几处擦

回收只在 bootloader 自己手里、且上一步已经通过授权时发生（上传、认领、换主、撤销都要先验签），
所以远程调用者逼不出一次擦除。**被拒绝的命令一律不写 flash**，见下。

## 上电：扫一遍

`bootloader_state_init()`：

```
从 metadata 区第一格（`0x081E4000`）往后扫
  │
  ├─ 0xFF（空）─────► 到头了，记下 next_free，结束
  │
  ├─ 'M'（7格）─────► last_metadata = 此处，i += 7，继续
  │                    （一路覆盖，所以最后留下的是最新那条）
  │
  └─ 其它 ──────────► 认不出，多半是旧版本布局写的
                       转为只读，等下一次成功上传时擦掉重来
```

**认不出就停，不猜长度往下走** —— 猜错一次就会落进别人记录的中间，之后读到的全是垃圾。

## 上电：拿它决定跳不跳

`server_decide()`：

```
crypto 自检过了吗？（sha256_selftest）
  │  否 ──► 一律当作无效。验证器本身都不可信，它的结论没有意义
  ▼
有 metadata 吗？
  │
  ├─ 没有 ─────────────────────────────────► app 无效
  │
  └─ 有 ──► app_size 在 (0, IAP_APP_MAX_SIZE] 吗？
             └─► 按 app_size 现算 app 区的 SHA-256
                  └─► 用 signature + cert 验签，并查这张叶有没有被撤销
                       ├─ 过 ───► app 有效 ──► 跳转进 app ✅
                       └─ 不过 ─► 停在 bootloader，身份报 BOOTLD-INVALID
```

**每次上电都验**，不是只在烧写后验一次 —— flash 会退化，也可能事后被改。

### 为什么是「验签」而不是「比对存好的哈希」

| | 只存哈希去比对 | 存签名去验证（现在） |
|---|---|---|
| 掉电半写、位翻转 | ✅ | ✅ |
| 有人重写 app 区 | ❌ **他也能把存的哈希一起改掉** | ✅ 没私钥签不出来 |

签名同时回答**完整性**（内容变了没有）和**真实性**（是不是持私钥的人签发的）。

⚠️ **它防的是损坏的镜像和远程注入，防不住手里拿着板子的人** —— 物理接触者可以用
ST-Link 直接重烧整片。这是刻意的取舍，见 `DECISIONS.md` 第 62 条。

## 被拒绝的认证只记在 RAM，绝不落 flash

**一次认证失败不会产生任何 flash 写入**，只在日志里打一行，带本次开机以来的失败次数和对端地址。

理由是拒绝服务：**未认证的调用者根本不该够得到 Flash** ——
否则一串被拒的命令就能磨损这个扇区，并逼出一次擦除。

原先还有一个 32 条的 RAM 环形缓冲，读取函数零调用者，2026-09-24 删掉（[决议 69](../../tables/DECISIONS.md)）。

## 「读不到 metadata」的两种情况

现象都是「停在 bootloader」，但原因不同。

| 情况 | 扫描时看到 | 串口现象 | 恢复 |
|---|---|---|---|
| **出厂空板 / 刚擦过** | 第一格就是 `0xFF` | `metadata absent` | 第一次上传就正常 |
| **上传中断 / 签名不过 / 叶被撤销** | 有 `M`，但验签失败 | `metadata present` + `App signature invalid` | 重传 |

⚠️ **事件日志删掉之后，这两种和「换了新 bootloader 读到旧布局」不再有独立的日志痕迹可查** ——
第三种会表现成第一种（旧记录认不出 → 擦掉 → 看起来像空板）。这是删日志的已知代价。
